# Chart Row Limit Evidence

This document preserves the detailed research that supports the durable policy in `../docs/ChartLimits.md`. It is evidence for one executable/catalog state, not a promise that addresses or internals remain stable.

## Verified Build

The investigation targeted the supported executable identity recorded by `../src/game/rva_catalog.json`. RVA references below are meaningful only under that catalog's timestamp and signature gates.

## Why The Parser Stops At 512 Rows

The generated piano-score row access path dispatches through source-row-specific code. The capped parser at RVA `0x39B3608` reserves for 512 entries and stops source traversal at the generated boundary. No generated row accessors exist for row 512 or above, so a direct continuation cannot recover all constructor inputs merely from the public row value.

The 512 boundary belongs to source extraction, not to every downstream array. Removing the branch without replacing the unavailable source access contract would make the parser read invalid generated state.

## What Is Not Limited To 512

The parsed chart stores dynamic external arrays:

- `chart+0x70`, `+0x78`, `+0x7C`: eight-byte array data, count, and capacity.
- `chart+0x80`, `+0x88`, `+0x8C`: `0x90`-byte event array data, count, and capacity.
- `chart+0x30`: maximum event time.
- `chart+0x34`: elapsed time.
- `chart+0xA0`: active flag.

The parser initially reserves 512 elements, but both append paths can grow allocations. `PianoChartUpdate` at RVA `0x39BA628`, completion scans, and the UI count loop iterate dynamic counts or end pointers. No second fixed 512-element gameplay, scoring, or text buffer was identified.

That observation is necessary but insufficient: dynamic capacity does not prove construction, ownership, links, UI, scoring, completion, or rollback beyond the generated source boundary.

## Ownership Hazard

A parsed `0x90` event is not safe to copy with `memcpy`. The deep-copy helper clones an owned subarray at event `+0x38/+0x40` and referenced state at `+0x60`. Links at `+0x10/+0x18` point into the event allocation and must be represented as indexes and rebased if that allocation moves. The link helper establishes those relationships.

This makes parser chunking, active-playback streaming, and uncontrolled destination reallocation unsafe approaches.

## Recovered Native ABI And Lifecycle

The full extraction is in [ChartEventAbiGhidra.txt](ChartEventAbiGhidra.txt), generated by [RecoverChartEventAbi.java](GhidraScripts/RecoverChartEventAbi.java).

| Helper | RVA and range | Shipping x64 ABI | Ownership effect |
| --- | --- | --- | --- |
| Parser | `0x39B3608`, `[0x39B3608,0x39B3BD0)` | `RCX=chart`, `RDX=event kind B`, `R8=event kind A` | Reserves native arrays, constructs/copies/links two temporaries per source row, then destroys both. |
| Constructor | `0x3987734`, `[0x3987734,0x398780E)` | `RCX=event`, `RDX=chart`, `R8=event kind`, `R9D=serial`; stack inputs include time, value, two bytes, and one qword | Initializes a `0x90` event with empty links, owned array, and referenced state. Returns `RCX` in `RAX`. |
| Deep copy | `0x3987624`, `[0x3987624,0x3987731)` | `RCX=destination`, `RDX=source` | Copies scalars and raw links, allocates/copies the owned subarray, and clones/addrefs referenced state. |
| Link | `0x398DB4C`, `[0x398DB4C,0x398DB67)` | `RCX=predecessor`, `RDX=child` | Writes predecessor/child links and moves the predecessor's former child. |
| Destructor | `0x3988A04`, `[0x3988A04,0x3988A2D)` | `RCX=event` | Releases referenced state and destroys the owned array. |

The parser has no encoded C++ unwind map to recover. Normal exits explicitly destroy both temporaries, but the executable provides no exception cleanup recipe reusable by an external tail writer. Transactional rollback therefore must be independently designed and proved.

## Safety Verdict

The constructor ABI and referenced-state lifecycle are recovered, but direct tail construction is not proven safe. The constructor's non-register inputs and later owned-array values come from generated row accessors. The retained runtime profile contains diagnostic identity/value metadata, not a proven one-to-one replacement for every generated field, grouping, camera, and owned-state input.

Native parse-into-temporary is not safer: a complete standalone chart constructor/destructor contract has not been established. Final-allocation stability, cross-boundary link rebasing, exception/failure rollback, and separate UI/completion consumers remain unproven.

Multiple chart objects or mutation during `PianoChartUpdate` are also unsafe assumptions. The owner exposes one persistent chart at `owner+0xF48`; callbacks, elapsed time, links, and scoring state are tied to it.

## Feasible Bypass Considered

The least speculative future path would require a fully recovered semantic mapping from retained source rows to every native constructor input, a single stable final allocation, index-based link planning and rebasing, destructor-safe rollback at each failure point, and independent qualification of UI, scoring, completion, camera/group behavior, and teardown. No such path is currently approved.

Patching only the parser cap, streaming tail events, copying parser temporaries, or appending guessed event bytes were rejected because each crosses an unproved ownership boundary.

## Experimental Implementation Status

The retained implementation is diagnostic-only and performs no parsed-event or parser-bound writes. `Experimental.ExtendedCharts=1` requests the experiment, validates executable identity and exact helper prologues, then remains fail closed at an effective 512-row runtime limit.

The verified diagnostic input limit is 1,024, but over-limit compilation is restricted to `diagnostic_extended_chart_fixture=true` and exactly 520 source rows. Compilation publishes rows 0-511 only. Rows 512-519 are retained as eight diagnostic values with explicit source identity. They are never placed in playable chart/profile vectors or selection, title, duration, completion, score, combo, UI, chart-hold, or native-write paths.

Per-song cache identity records the row policy, accepted input limit, diagnostic bit, and policy generation. Ordinary songs normalize to native-512/disabled identity regardless of the global request. A diagnostic cache cannot load when the experiment is disabled or helper validation changes.

The offline synthetic model covers boundary sizes, rows around the boundary, pitch/chord identity, camera/group transitions, final onset, ownership isolation, links, display count, default-disabled guards, and injected rollback points. It proves no native ABI, runtime event construction, or playable greater-than-512 behavior.

## Single Runtime Qualification Plan

The diagnostic fixture tool creates an exactly-520 `song.json` plus silent audio in a new staging directory. A manually staged diagnostic build may enter that fixture once, allow the native prefix to complete, and leave once.

One run can prove only source/profile identity, source count 520, selected prefix 512, tail count 8, immediate native prefix layout, and prefix lifecycle survival. Identity and pointer/bounds checks gate detailed event logging. Rows 512-519 intentionally produce no events, do not hold completion, and do not alter duration.

The run cannot prove tail construction, links, ownership, camera/group behavior, UI/score contribution, or playable greater-than-512 readiness.

## Exact Runtime Result, 2026-07-15

The ignored session input `FF7RPianoSongs-v38-route-leak-520-20260715.log` contained captures from the focused run. The durable findings retained here are that the ordinary song was correctly rejected by the extended identity gate while its registry/owner/wrapper/caller checks passed, and that the exact-520 fixture passed policy, descriptor, registry, owner, wrapper, caller, source/prefix/tail, and bounded chart-read checks. The native prefix remained 512 and the retained tail remained diagnostic-only. Any future claim from the raw log must first preserve its relevant bounded excerpts or derived findings in tracked evidence.

The result validates the read-only evidence path, not a bypass. No runtime tail event was constructed and no greater-than-512 claim is supported.

## Current Policy

The shipping/playable boundary remains 512. The larger accepted-input constant is diagnostic-only, conditionally enabled, and never a publication limit. Any future change requires new ABI/ownership proof, transactional implementation, full automated coverage, and explicit in-game qualification of every affected consumer.
